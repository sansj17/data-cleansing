# Case Study: Understanding and Cleansing a Supplier Database with AI Agent Skills

Handoff brief for Claude Code. Read this file first, then start with the checklist at the bottom.

## Background

This is a 35–40 minute demo for a Friday coding club, where members showcase coding tips, tricks and repositories. Previous showcases covered Graphify, Ponytail, REA, Ghostty and uv.

This session shows how two sets of agent skills can help someone understand an unfamiliar database and carry out a quick data cleansing exercise:

- **Matt Pocock's skills** (`mattpocock/skills`): `ubiquitous-language`, `grill-me`, `to-prd`, `to-issues`, `tdd`, `handoff`
- **Cathryn Lavery's diagram-design** (`cathrynlavery/diagram-design`): editorial diagrams saved as HTML, SVG or PNG

## Goals

1. Show an agent **explaining** a database it has never seen: its schema, its vocabulary and its relationships.
2. Show the agent **finding** data quality problems and visualizing their root causes.
3. Show the agent **challenging** the cleansing rules before any code is written.
4. Show **test-first** fixes that prove each rule works.
5. Finish with clear **before and after** results and a visual of where every record went.

## Scenario

"We've inherited a supplier database ahead of an ERP (Enterprise Resource Planning) migration. Before we load it into the new system, we need to understand what's in it and fix the worst problems."

All data is **synthetic**. No real client or company data is used.

## Tech stack

- **uv** for the Python project and dependencies
- **DuckDB** as a single-file database (`suppliers.duckdb`)
- **Python 3.12+** with `faker` for realistic names and addresses, and `pytest` for tests
- Optional: **marimo** for a before and after metrics notebook, **Graphify** for a final map of the repository

## Dataset specification

The data is generated by `generate_data.py` from a **fixed random seed (42)**, so every run produces the same database and the answer key stays valid.

### Tables

**`vendors`** (target: 200 rows after planted duplicates are added)

| Column        | Type    | Notes                                                                                                |
| ------------- | ------- | ---------------------------------------------------------------------------------------------------- |
| vendor_id     | INTEGER | Primary key                                                                                          |
| vendor_name   | VARCHAR | Company name                                                                                         |
| tax_id        | VARCHAR | Format `NN-NNNNNNN` when valid                                                                       |
| country       | VARCHAR | Should be an ISO (International Organization for Standardization) 3166 two-letter code, such as `CA` |
| email         | VARCHAR | Accounts payable contact                                                                             |
| payment_terms | VARCHAR | Should be one of `NET30`, `NET45`, `NET60`                                                           |
| status        | VARCHAR | `active` or `inactive`                                                                               |
| created_date  | VARCHAR | Should be ISO 8601 (`YYYY-MM-DD`). It is stored as text on purpose, so that mixed formats can exist  |

**`purchase_orders`** (target: about 800 rows)

| Column    | Type          | Notes                                                                                                          |
| --------- | ------------- | -------------------------------------------------------------------------------------------------------------- |
| po_id     | INTEGER       | Primary key (PO = Purchase Order)                                                                              |
| vendor_id | INTEGER       | References `vendors.vendor_id`. Deliberately **no** foreign key constraint, so that orphaned records can exist |
| po_date   | DATE          |                                                                                                                |
| amount    | DECIMAL(12,2) |                                                                                                                |
| currency  | VARCHAR       | `CAD`, `USD`, `MXN`                                                                                            |

**`invoices`** (target: about 1,500 rows)

| Column       | Type          | Notes                                                                          |
| ------------ | ------------- | ------------------------------------------------------------------------------ |
| invoice_id   | INTEGER       | Primary key                                                                    |
| po_id        | INTEGER       | References `purchase_orders.po_id`. Deliberately **no** foreign key constraint |
| invoice_date | DATE          |                                                                                |
| amount       | DECIMAL(12,2) |                                                                                |
| paid         | BOOLEAN       |                                                                                |

### Planted problems (exact counts)

| #   | Problem                                                                           | Table           | Count                         | Example                                              |
| --- | --------------------------------------------------------------------------------- | --------------- | ----------------------------- | ---------------------------------------------------- |
| P1  | Near-duplicate vendors: the same company under name variants, sharing a tax ID    | vendors         | 12 clusters, 30 rows in total | "ACME Corp", "Acme Corporation", "ACME CORP."        |
| P2  | Inconsistent country values                                                       | vendors         | 40 rows                       | "Canada", "CAN", "ca", "Méx", "USA", "United States" |
| P3  | Missing tax ID (NULL or empty string)                                             | vendors         | 18 rows                       | `NULL`, `''`                                         |
| P4  | Malformed tax ID                                                                  | vendors         | 9 rows                        | `123456789`, `12-34567`, `AB-1234567`                |
| P5  | Invalid email                                                                     | vendors         | 14 rows                       | `ap@acme`, `billing.acme.com`, `n/a`                 |
| P6  | Inconsistent payment terms                                                        | vendors         | 35 rows                       | "Net 30", "N30", "30 days", "net-45"                 |
| P7  | Mixed date formats in `created_date`                                              | vendors         | 25 rows                       | `03/15/2021`, `15-Mar-2021`, `2021.03.15`            |
| P8  | Orphaned purchase orders (the vendor doesn't exist)                               | purchase_orders | 22 rows                       | `vendor_id` 9001                                     |
| P9  | Orphaned invoices (the purchase order doesn't exist)                              | invoices        | 11 rows                       | `po_id` 99001                                        |
| P10 | Purchase orders still pointing to a duplicate vendor record that should be merged | purchase_orders | about 60 rows                 | Will need re-pointing after the P1 merge             |

Some rows will have more than one problem. That's intentional, because real data looks like this.

### Answer key

`generate_data.py` must also write `answer_key.json`. For each problem ID (P1–P10), it lists the affected primary keys and, for P1, the duplicate clusters with the intended surviving record.

The answer key is for the presenter only. **Do not show it to the agent during the demo.** The agent should find the problems on its own. The answer key is used afterwards to score how much it found.

## Session flow

| Step            | Time   | What happens                                                                                                                                                                                                                | Tools                                     |
| --------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| 0. Setup        | 2 min  | Done before the session. Project created, database generated, skills installed. `/setup-matt-pocock-skills` configured with **local files** as the issue tracker                                                            | uv, DuckDB                                |
| 1. Understand   | 8 min  | Agent inspects schema and sample rows. Builds a glossary (data dictionary). Draws an ER (Entity-Relationship) diagram                                                                                                       | `ubiquitous-language`, diagram-design     |
| 2. Profile      | 7 min  | Agent runs profiling queries for null rates, near-duplicates, orphaned records and inconsistent values. Draws a fishbone (Ishikawa) diagram of likely root causes                                                           | DuckDB, diagram-design                    |
| 3. Decide rules | 5 min  | Agent challenges the cleansing plan: which record survives a merge, whether to delete or set aside orphans, whether a missing tax ID blocks migration. Rules become a short PRD (Product Requirements Document) and tickets | `grill-me`, `to-prd`, `to-issues`         |
| 4. Fix          | 10 min | Two tickets worked test-first. Suggested tickets: "standardize country codes" (simple) and "merge duplicate vendors and re-point purchase orders" (impressive)                                                              | `tdd`, optionally Ponytail                |
| 5. Results      | 5 min  | Before and after metrics. Sankey diagram showing raw rows flowing into clean, merged, or set aside for review                                                                                                               | DuckDB, diagram-design, optionally marimo |
| 6. Wrap-up      | 2 min  | Handoff document. Key point: the agent explained, challenged, proved and visualized                                                                                                                                         | `handoff`                                 |

### Cleansing principles to apply in step 4

- **Never delete.** Records that can't be fixed go to a `quarantine_*` table along with a reason.
- **Keep the raw data untouched.** Cleansed output goes to `clean_*` tables or a separate schema.
- **Every rule has a test.** For example: "no two active vendors share a tax ID", "every purchase order references an existing vendor", "every country value is a valid two-letter code".
